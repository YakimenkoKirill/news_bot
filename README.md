# news_bot

Бот собирает новости из RSS-лент, сайтов без RSS и открытых Telegram-каналов, отсеивает дубли и неподходящие материалы, пересказывает их через DeepSeek и публикует пересказ в Telegram-канал. Управление источниками, ключевыми словами и модерацией — через отдельного бота для администраторов.

Как устроен пайплайн:

```
сбор (RSS, сайты, Telegram) -> нормализация, фильтры, дедупликация -> пересказ DeepSeek
    -> модерация (по желанию) -> публикация в канал по расписанию
```

Каждая стадия меняет статус новости в БД (`new -> normalized -> processed -> approved -> published` и ветки `duplicate`, `filtered`, `pending_review`, `rejected`, `failed`). Правила для разработчиков и ИИ-исполнителей — в [CLAUDE.md](.claude/CLAUDE.md).

## Требования

- Python 3.11+ и `make`;
- Docker и Docker Compose v2 (PostgreSQL 16 для разработки и боевой запуск);
- бот Telegram (токен у [@BotFather](https://t.me/BotFather)), добавленный администратором канала с правом публикации;
- `api_id` и `api_hash` приложения Telegram с [my.telegram.org](https://my.telegram.org) — для чтения каналов-источников;
- ключ API DeepSeek или совместимого с OpenAI сервиса.

## Установка и запуск локально

```bash
make install                  # .venv и зависимости
cp -n .env.example .env       # только при первой установке: -n не перезапишет готовый .env
make db-up                    # PostgreSQL 16 в Docker (+ БД для тестов)
make migrate                  # схема БД
.venv/bin/python scripts/telethon_login.py   # разовый вход Telethon, см. ниже
.venv/bin/python -m app       # запуск; остановка — Ctrl+C или SIGTERM
```

Проверки: `make lint`, `make test` (unit), `make test-integration` (нужны `make db-up` и `TEST_DATABASE_URL`), `make coverage`.

Если порт 5432 занят другим PostgreSQL, задайте в `.env` `POSTGRES_PORT=5433` и этот же порт в `DATABASE_URL` и `TEST_DATABASE_URL`.

## Первый вход Telethon

Telethon читает каналы-источники от имени вашего аккаунта Telegram. Вход делается один раз и сохраняет файл сессии `TELETHON_SESSION_PATH.session`:

```bash
.venv/bin/python scripts/telethon_login.py
```

Скрипт спросит номер телефона, код из Telegram и пароль 2FA. Файл сессии даёт полный доступ к аккаунту: не коммитьте его (каталог `data/` в `.gitignore`) и храните как секрет. Без сессии приложение не стартует и пишет, что нужно выполнить этот скрипт. Читаются только публичные каналы с username.

## Работа с ботом управления

Пишут боту только администраторы (`TELEGRAM_ADMIN_IDS` и таблица `admins`), остальные получают отказ.

| Команда | Что делает |
| --- | --- |
| `/start`, `/help` | приветствие, меню и список команд |
| `/status` | новости по статусам, проблемные источники, расход DeepSeek за сутки и бюджет, пауза, время последней публикации |
| `/queue` | подготовленные посты: очередь публикации и посты на модерации, предпросмотр, публикация вне очереди |
| `/errors` | журнал ошибок: что сломалось, сколько раз, повтор упавших новостей |
| `/report` | отчёт за сегодня, вчера или 7 дней |
| `/pause`, `/resume` | остановить и возобновить обработку моделью и публикацию (сбор продолжается) |
| `/sources` | список источников; кнопки «вкл/выкл», «удалить» (с подтверждением), «проверить» (пробный сбор) |
| `/add_source` | диалог добавления: тип (rss, web, tg) -> адрес -> имя -> интервал -> режим модерации -> для сайтов CSS-селекторы JSON -> «Пробный сбор» или «Сохранить» |
| `/keywords` | ключевые слова (новость должна содержать хотя бы одно) и стоп-слова; добавление через запятую, удаление кнопками |
| `/cancel` | выйти из текущего диалога |

Селекторы для сайта без RSS: `{"list_item": "article.news", "link": "a", "title": "h2"}` — `list_item` выделяет карточку статьи на странице-списке, `link` — ссылку в ней, `title` — заголовок (необязательно).

**Модерация.** У источника с режимом `review`, а также у любого поста, где проверка нашла цифры или имена, которых нет в источнике, пост сначала приходит администраторам в том виде, в каком выйдет в канал. Кнопки: «Опубликовать» (в очередь публикации), «Изменить» (прислать новый текст пересказа), «Отклонить», «Позже» (повторно придёт через `moderation.snooze_min`). Решение одного админа видно остальным: повторное нажатие ответит «Уже обработано».

### Один экран в чате

В чате с ботом висит только последний ответ — история не копится. Ваши команды бот тоже удаляет после обработки, поэтому чат остаётся чистым.

**Что считается одним экраном:**

- ответ на одну команду или одно нажатие кнопки, даже если это несколько сообщений;
- один алерт (каждому администратору — свой экран);
- заметка «Проверьте перед публикацией» вместе с черновиком поста;
- все части ежедневного отчёта.

Новый экран приходит на смену прошлому. Алерт или черновик на модерацию заменят список, с которым вы работали, но **ничего не теряется**: черновики лежат во вкладке «На модерации» в `/queue`, ошибки — в `/errors`, отчёт — в `/report`.

Telegram разрешает боту удалять сообщения не старше 48 часов. Экран старше этого срока останется в истории — это не ошибка, бот просто пропустит его.

Нижнее меню команд из `/start` — это клавиатура, а не сообщение: она никуда не денется.

**Как выключить:**

| Что нужно | Как |
| --- | --- |
| Вернуть обычную переписку | `UI__SINGLE_SCREEN=false` или `ui.single_screen: false` |
| Оставить свои команды в чате, но менять экраны бота | `UI__DELETE_USER_MESSAGES=false` |

Посты в канале это не затрагивает никогда: экраны работают только в личных чатах с администраторами.

### Очередь публикации и /queue

Посты выходят не по времени сбора, а по приоритету:

```
приоритет = оценка интереса
          − publisher.score_decay_per_h × возраст в часах
          + publisher.cluster_bonus × min(источников события − 1, publisher.cluster_bonus_max)
```

Оценка интереса (0…1) — это `score` модели, возраст считается от времени публикации в источнике (если его нет — от времени сбора). При `score_decay_per_h: 0.02` новость двенадцатичасовой давности теряет 0,24, поэтому свежая новость с оценкой 0,6 выйдет раньше вчерашней с 0,8. Коэффициент `0` — порядок только по оценке; чем он больше, тем важнее свежесть. Отбор по `ai.min_score` не меняется: приоритет только упорядочивает посты, которые уже прошли отбор.

**Бонус за число источников.** Если о том же событии написал другой источник, его новость уходит в `duplicate`, а у первой (корневой) новости кластера растёт счётчик `cluster_sources`. За каждый источник сверх первого приоритет повышается на `publisher.cluster_bonus` (по умолчанию 0,05), но не больше чем за `publisher.cluster_bonus_max` источников (по умолчанию 3): десять источников дают столько же, сколько четыре. Так событие, которое заметили все, выходит раньше. Дубль из того же источника счётчик не меняет — считаются только разные источники. `cluster_bonus: 0` возвращает прежний порядок. В канал ни имена источников, ни их число не выводятся: это только приоритет очереди, пометку `🔁N` видят лишь администраторы в `/queue`.

`/queue` показывает две вкладки:

- **В очереди** (`approved` и `scheduled`) — порядок совпадает с порядком выхода в канал. У каждого поста видна оценка (★0.82) и ожидаемое время выхода «≈12:40». Время — оценка: новые интересные посты могут встать выше, а пауза и сбои его сдвигают. На паузе время не показывается. Пост, который прямо сейчас отправляется, помечен «⏳ отправляется» — его нельзя опубликовать вне очереди, кнопка ответит «Пост сейчас публикуется». Пометка «🔁3» означает, что об этом событии написали три источника.
- **На модерации** (`pending_review`) — в том же порядке, ⚠️ отмечает посты с замечанием проверки фактов.

Кнопка «👁 N» присылает предпросмотр поста ровно в том виде, в каком он выйдет в канал. Под ним — «🚀 Опубликовать сейчас» с подтверждением: пост выходит сразу, без учёта интервала между постами, тихих часов и паузы, но с теми же лимитами длины и проверкой картинки, что и обычная публикация. Пост с модерации при этом считается одобренным. После ручного поста обычная очередь ждёт `publisher.min_interval_min`. Двойное нажатие или два админа не опубликуют пост дважды: второй получит «Уже обработано».

### Как идёт публикация

Один пост публикуется в три шага, чтобы соединение с базой не было занято во время обращений к сети:

1. Короткая транзакция: пост с наибольшим приоритетом захватывается (`approved` -> `scheduled`, то есть «отправляется»), и всё нужное для поста читается из базы.
2. Без транзакции: картинка (проверка URL по HTTP, а у новостей из Telegram — загрузка фото исходного сообщения через Telethon) и отправка в Telegram с повторами при `FloodWait`.
3. Короткая транзакция: запись о публикации и `scheduled` -> `published`, либо запись об ошибке, `scheduled` -> `failed` с причиной `publish_error` и алерт.

Пока пост в `scheduled`, очередь его не берёт, поэтому один пост не уходит в канал дважды. Место в лимите источника он при этом занимает.

**Если приложение упало между шагами 2 и 3**, пост остаётся в `scheduled`, и по базе не понять, вышел он в канал или нет. Такие посты разбираются при старте и каждые `scheduler.recover_every_min` минут (по умолчанию 10): пост, который висит дольше `publisher.stuck_after_min` минут (по умолчанию 15), переводится в `published`, если запись о публикации всё-таки есть, иначе — в `failed` с причиной `publish_unknown`, и администратор получает алерт «Проверьте канал: пост мог выйти». Сам бот повторно не отправляет: иначе в канале мог бы появиться дубль. Если пост не вышел, его возвращают в очередь кнопкой «Повторить» в `/errors` -> «Новости».

### Лимит источника в очереди

В очереди публикации держится не больше **`publisher.max_queued_per_source`** постов одного источника (по умолчанию 4). Остаются самые сильные по приоритету — та же оценка с поправкой на свежесть, по которой строится порядок выхода.

Лишний пост уходит в `filtered` с причиной `queue_limit` и в канал уже не попадёт. Это нужно, чтобы один болтливый источник не занял всю ленту: без лимита РБК с сотней новостей в день вытеснил бы всех остальных просто количеством.

| Что происходит | Проверяется лимит |
| --- | --- |
| Модель одобрила пост | Да. Слабее всех в очереди — отсеивается |
| Админ нажал «Опубликовать» на модерации | Да, но пост проходит всегда: вытесняется слабейший автоматический пост |
| Админ поправил текст пересказа | Так же, проходит всегда |
| «🔁 Повторить» в `/errors` | Так же, проходит всегда |
| «🚀 Опубликовать сейчас» в `/queue` | Нет: пост сразу уходит в канал и в очереди не оседает |

**При старте** приложение приводит очередь к лимиту: если вы уменьшили значение или включили лимит впервые, лишнее вытесняется сразу.

**Где это видно:**

- `/queue` — рядом с источником его заполненность: `Пример 2/4`, а при полной очереди `🔒4/4`;
- `/status` — строка «Очередь заполнена у источников: Bell 4/4»;
- ежедневный отчёт — в воронке «вытеснено лимитом источника N» и строка «Вытеснено лимитом: Bell 3» под таблицей источников.

**Отключить:** `PUBLISHER__MAX_QUEUED_PER_SOURCE=0` или `max_queued_per_source: 0` в конфигурации.

Учтите: вытесненная новость уже прошла через модель, то есть деньги на неё потрачены. Если вытеснений много, выгоднее поднять `ai.min_score` или реже опрашивать болтливые источники, чем отсеивать уже оплаченные пересказы.

### Что уходит в канал

Пост состоит из заголовка, пересказа и подписи канала:

```
Заголовок жирным

Пересказ своими словами.

🔵 try_1          ← название канала, в нём ссылка
```

Подпись настраивается в секции `publisher`, без правки кода:

| Ключ | Что задаёт |
| --- | --- |
| `footer_mark` | Знак перед названием (сейчас `🔵`); пустой — только название |
| `footer_title` | Видимый текст ссылки |
| `footer_url` | Куда ведёт ссылка; **пустой — подписи не будет** |

**Картинка.** У новостей из RSS и с сайтов берётся картинка по адресу из статьи: она проверяется по типу и размеру (`publisher.image_types`, `publisher.image_max_bytes`). У новостей из Telegram публичного адреса у фото нет, поэтому фото исходного сообщения скачивается через Telethon и уходит файлом; у альбома берётся первое фото. Если фото нет, оно больше лимита, сообщение удалено или Telethon недоступен, пост выходит текстом — как раньше. Предпросмотр в боте показывает ту же картинку, что уйдёт в канал.

Ни хэштегов, ни подписи «Источник», ни ссылки на оригинал в посте нет. Превью ссылки Telegram не показывает: иначе под каждым постом появлялась бы карточка канала. Ссылка на источник и его имя сохраняются в базе (их видно в `/queue` и в отчёте), но в канал не попадают. Чтобы вернуть хэштеги, поставьте `channel.hashtags_max` больше нуля.

## Ежедневный отчёт

Каждую ночь в **00:05** по `app.timezone` все администраторы получают отчёт за прошедшие сутки. Время выбрано внутри тихих часов и уже после полуночи, поэтому в отчёт попадают все публикации дня, включая вышедшие с 23:30 до 00:00. Поменять: `daily_report.send_at` в конфигурации или переменная `DAILY_REPORT__SEND_AT=22:00`. Отключить: `daily_report.enabled: false` — команда `/report` при этом продолжит работать.

**`daily_report.report_day`** решает, за какие сутки отчёт:

| Значение | Отчёт | Когда полезно |
| --- | --- | --- |
| `previous` (по умолчанию) | За вчерашние сутки целиком, 00:00–24:00 | Отправка после полуночи: день закрыт, цифры окончательные |
| `current` | За сегодня до момента отправки | Отправка вечером того же дня |

По умолчанию стоит `previous`: при отправке вечером часть публикаций остаётся за границей отчёта и не попадает ни в него, ни в следующий — он уже за другие сутки. Если поставить `current` и время отправки вне `publisher.quiet_hours`, при запуске в лог уйдёт предупреждение `config.inconsistent`: отчёт за текущие сутки уйдёт до конца публикаций. Это предупреждение, а не ошибка — приложение запустится.

Отчёт уходит ровно один раз за отчётный день: в настройке `daily_report_last` хранится дата **отчётного** дня, а не дата отправки. Поэтому перезапуск в 00:20 после отправки отчёт не повторит. Если бот не работал в 00:05, отчёт за вчера придёт при первом запуске задачи в тот же день — например в 09:00. Два запущенных экземпляра пришлют один отчёт: дата читается с блокировкой строки.

**Что в отчёте:**

| Блок | Что показывает |
| --- | --- |
| Итог | Опубликовано, собрано, потрачено — со стрелками ▲▼ к прошлому периоду |
| Публикации | По расписанию и вне очереди, отредактированные, неудачные, самый активный час, лучшие посты со ссылками |
| Источники | Таблица: собрано, в канал, дубли, отсев, средняя оценка. ⚠️ — есть ошибки, ⏸ — выключен |
| Воронка | Путь новостей: собрано → дубли → фильтры → модель → не по теме → модерация → очередь → опубликовано |
| Модель | Расход и доля дневного бюджета (⚠️ с `budget_warn_share`), запросы (отдельно отбор и пересказ), токены, доля входных токенов из кэша, неудачные запросы, цена поста, расход с начала месяца |
| Качество | Задержка, средняя оценка, дубли в канале, отклонения модератором — с ✅/❌ по целям из секции `metrics` |
| Сейчас | Сколько в очереди и на модерации, лучший пост очереди |
| Читатели | Просмотры, пересылки и реакции постов со собранной статистикой, лучшие по просмотрам, просмотры на пост по источникам |
| Ошибки | Открытые инциденты и новые за период |

**Откуда берётся расход.** Каждый запрос к модели — строка в таблице `ai_requests`: токены, из них кэшированные, стоимость и признак «ответ разобран». Пишутся и неудачные попытки, поэтому сумма за сутки равна реально оплаченному, даже если пересказа так и не появилось и новость ушла в `failed`. По этой же таблице считают дневной бюджет, `/status` и `scripts/run_report.py` — цифры везде одинаковые. Кэшированные входные токены стоят `ai.price_input_cached_per_1m`; пока этот ключ не задан (его значение зависит от провайдера), они считаются по обычной цене входа — расход тогда завышен, но не занижен.

**Как считаются цифры.** Публикации берутся по времени выхода в канал, а воронка — по времени сбора новости. Поэтому новость, собранная вчера и опубликованная сегодня, попадёт в «Публикации», но не в сегодняшнюю воронку. Сутки считаются по `app.timezone`, а не по UTC. Сравнение со вчера — это тот же период предыдущих суток; для «сегодня» сравнение идёт со вчерашним днём до того же часа.

**Команда `/report`** присылает тот же отчёт за сегодня, вчера или последние 7 полных суток — кнопками под сообщением. Метрики те же, что считает `scripts/run_report.py`: общий код в `app/reports/metrics.py`, поэтому цифры в боте и в скрипте совпадают.

## Ошибки и алерты

Каждое событие — сбой источника, недоступность модели, ошибка публикации, сбой фоновой задачи — попадает в журнал ошибок, даже если сообщение в чат не ушло. В журнал пишутся и повторы, подавленные `alerts.throttle_min`, и виды, отключённые в чате. Если упала база, алерт всё равно придёт в чат.

**Инцидент, а не событие.** Повторы с одним ключом копятся в одной записи: растёт счётчик, обновляется время и текст. Поэтому «источник не отвечает ×47» — это одна строка, а не 47. Закрытый инцидент больше не наполняется: следующее событие с тем же ключом открывает новый.

**`/errors`** показывает три вкладки:

- **Открытые** — то, что сейчас сломано. Заголовок считает открытые инциденты по видам.
- **Все** — вместе с закрытыми, они помечены ✅.
- **Новости** — новости в статусе `failed`, с причиной.

Кнопка «🔎 N» открывает карточку: ключ, первый и последний раз, число повторов, статус и полный текст.

| Кнопка | Что делает |
| --- | --- |
| ✅ Решено | Закрывает инцидент. Следующее такое же событие откроет новый — видно, что проблема вернулась |
| ✅ Решить все | Закрывает все открытые, с подтверждением |
| 🔕 Не присылать в чат | Вид перестаёт приходить сообщением, но пишется в журнал. Действует сразу, перезапуск не нужен. Обратно — «🔔 Присылать в чат» |
| 🔁 Повторить | Возвращает упавшую новость в работу |

Виды из `alerts.silent_kinds` (по умолчанию `ai_item_failed` — модель не смогла обработать отдельную новость) в чат не приходят никогда: такие ошибки обычно единичны и шумят. Снять это кнопкой нельзя, только правкой конфигурации.

**Что делает «Повторить»** зависит от причины:

| Причина | Куда вернётся |
| --- | --- |
| `bad_ai_response` — модель вернула некорректный ответ или обрезала его по `ai.max_output_tokens` | Снова в модель; обработка потратит бюджет как обычно |
| `publish_error` — не удалось опубликовать | В очередь публикации, выйдет по приоритету |
| `publish_unknown` — неизвестно, вышел ли пост | В очередь публикации; сначала проверьте канал, иначе будет дубль |
| `no_processed_post` — нет пересказа | Снова в модель |

Если новость уже повторил другой администратор, бот ответит, что она не в статусе `failed`.

**Сколько хранится.** Закрытые инциденты старше `alerts.retention_days` (30 дней) удаляются фоновой задачей раз в `scheduler.purge_every_h` часов. Открытые не удаляются никогда. Число открытых ошибок видно в `/status`.

## Настройки без перезапуска

Часть параметров меняется на лету: значение из БД важнее значения из `configs/*.yaml`, и его видят ближайшие запуски задач — не позже `runtime.cache_s` секунд (по умолчанию 30). Перезапуск не нужен.

| Параметр | Что задаёт | Допустимые значения |
| --- | --- | --- |
| `channel.topic` | тематика канала в промпте | текст от 3 до 200 символов |
| `ai.min_score` | порог интереса новости | число от 0 до 1 |
| `publisher.min_interval_min` | интервал между постами | минуты, не меньше 1 |
| `publisher.quiet_hours` | тихие часы | «23:00-07:00» или пусто |
| `publisher.max_queued_per_source` | постов источника в очереди | целое, 0 — без лимита |
| `publisher.score_decay_per_h` | старение оценки за час | неотрицательное число |

Переопределения лежат одним значением `runtime_overrides` в таблице `settings`. Значение из yaml остаётся значением по умолчанию: если переопределение убрать, параметр снова берётся из конфигурации, а `ENV`-переменные по-прежнему задают именно эти значения по умолчанию при старте.

Неверное значение не записывается: в ответ приходит понятная ошибка. Если значение в БД испортили руками, приложение логирует `runtime.bad_override`, игнорирует этот параметр и работает по yaml. После уменьшения `publisher.max_queued_per_source` лишние посты источников вытесняются сразу, как при старте.

Менять эти параметры из бота умеет команда `/settings` — она появится следующим шагом; пока значения задаются через `RuntimeConfig` в коде и видны в логах `runtime.set` и `runtime.reset`.

## Иностранные источники

По умолчанию в канал идут только русскоязычные новости: `filters.allowed_languages: ["ru"]`. Чтобы добавить англоязычные источники:

1. Впишите язык в конфигурацию: `filters.allowed_languages: ["ru", "en"]` (или `FILTERS__ALLOWED_LANGUAGES='["ru","en"]'`). Без этого новости отсеются фильтром языка ещё до модели.
2. Добавьте сами источники через бота (`/sources` -> «Добавить») или включите уже добавленные.
3. Первое время оставьте `ai.review_foreign: true` — переводы будут приходить на модерацию, даже если источник работает автоматически. Когда качество перевода устроит, поставьте `false`, и переводы пойдут по режиму источника.

**Что делает модель.** В промпт передаётся язык источника (`Язык источника: en`) и правило: если язык источника отличается от языка канала (`channel.language`), пересказ пишется на языке канала; имена и названия компаний — общепринятым написанием, при сомнении — с оригиналом в скобках.

**Проверка фактов у переводов** сверяет только числа: записи «1,000», «1 000» и «1000» приводятся к одному виду, как и «1,5» с «1.5». Имена не сверяются — в переводе они написаны другими буквами, и сравнение давало бы ложные замечания. Поэтому в замечании к посту появляется пометка «перевод из en: имена не проверены автоматически»: имена проверяет человек. Новости на языке канала проверяются как раньше — и числа, и имена.

## Статистика постов канала

Через `stats.delay_h` часов после выхода поста (по умолчанию через сутки) задача `post_stats` читает его в канале аккаунтом Telethon и сохраняет в `publications`:

| Поле | Что |
| --- | --- |
| `views` | просмотры |
| `forwards` | пересылки |
| `reactions` | сумма реакций всех видов; 0 — реакции выключены или их нет |
| `stats_at` | когда статистика собрана |

Задача запускается раз в `scheduler.stats_every_min` минут (по умолчанию раз в час) и берёт только посты, у которых `stats_at` пуст, — уже собранное не перезапрашивается. Пост, удалённый из канала, получает `stats_at` с пустыми значениями. Посты старше `stats.max_age_h` (по умолчанию 72 часа) тоже отмечаются пустыми: статистику уже не получить, и опрашивать их вечно не нужно.

Собранные цифры попадают в блок «Читатели» ежедневного отчёта: сколько прочитали всего и в среднем на пост, какие посты читали больше остальных и сколько просмотров на пост дают разные источники. Пока статистики нет, блок не выводится.

**Что нужно от человека.** Аккаунт Telethon должен видеть канал: быть его участником или администратором. Иначе в журнал `/errors` попадёт инцидент `stats_unavailable` («Статистика канала недоступна»), а задача продолжит работать — сбор просто не даст цифр. В чат этот вид не присылается: он есть в `alerts.silent_kinds`.

## Очистка старых текстов

Тексты новостей — основная часть объёма базы, и для новостей, которые уже никуда не двинутся, они не нужны. Раз в `scheduler.retention_every_h` часов (по умолчанию раз в сутки) задача `retention` очищает их у новостей в конечных статусах (`published`, `filtered`, `duplicate`, `rejected`), созданных больше `retention.text_days` дней назад (по умолчанию 30).

| Что | Становится |
| --- | --- |
| `raw_text` | пустая строка |
| `clean_text` | `NULL` |

**Остаётся всё остальное:** заголовок, адрес, канонический URL, хеш содержимого, SimHash с частями, `cluster_id`, `raw_meta` (в нём, например, id сообщения Telegram и картинки). Поэтому поиск дублей, отчёты, `/queue` и `/errors` работают как раньше: пересказ лежит отдельно, в `processed_posts`, и не очищается.

Новости в работе — `new`, `normalized`, `processed`, `pending_review`, `approved`, `scheduled`, `failed` — не очищаются никогда, сколько бы ни ждали.

**Срок** меняется в `retention.text_days` (или `RETENTION__TEXT_DAYS=60`). Он не может быть меньше окна поиска дублей `dedup.window_h`: иначе бот перестал бы узнавать дубли, поэтому такое значение отклоняется при запуске. За один запуск задача работает не дольше `retention.max_run_s` секунд и чистит пачками по `retention.batch_size`; если новостей больше, остальные очистит следующий запуск. Занятые другими транзакциями строки пропускаются, так что сбор и нормализация не ждут очистку.

## Как обновить промпт

Промпты — в `app/pipeline/ai/prompts.py`. После изменения текста повысьте `PROMPT_VERSION` (например `v3` -> `v4`): версия сохраняется в `processed_posts.prompt_version`, и по ней видно, какие посты сделаны каким промптом. Профиль канала (тема, тон, лимиты) меняется в секции `channel` без правки кода.

### Два запроса вместо одного

Новость обрабатывается в два шага, потому что выходные токены в четыре раза дороже входных, а «не по теме» — большинство новостей:

1. **Отбор** (`build_screen_messages`): модель получает заголовок и первые `ai.screen_input_chars` символов текста и отвечает только `relevant` и `score`. Ответ ограничен `ai.screen_max_tokens` токенами. Системное сообщение не содержит меняющихся данных — у провайдера срабатывает кэш входных токенов.
2. **Пересказ** (`build_messages`): запрашивается только для новостей, прошедших отбор. Промпт больше не спрашивает оценку — её даёт отбор, она же попадает в `processed_posts.relevance_score`.

Новость «не по теме» или с оценкой ниже `ai.min_score` уходит в `filtered` после первого короткого запроса: пересказ не запрашивается и пересказ в базе не появляется. Каждый запрос пишется в `ai_requests` со своим `kind` (`screen` или `summary`), поэтому в отчёте видно, сколько стоил отбор и сколько пересказ.

**Откатиться к одному запросу** можно без деплоя прежней версии: `ai.two_stage: false` (или `AI__TWO_STAGE=false`). Тогда работает промпт `v3` — оценка и пересказ в одном ответе, как раньше.

## Деплой

На сервере нужны Docker и Docker Compose. В `.env` на сервере `DATABASE_URL` указывает на сервис БД внутри compose:

```
DATABASE_URL=postgresql+asyncpg://news:<пароль>@postgres:5432/news
POSTGRES_USER=news
POSTGRES_PASSWORD=<пароль>
POSTGRES_DB=news
```

```bash
make docker-build
docker compose -f docker/docker-compose.prod.yml run --rm app python scripts/telethon_login.py
docker compose -f docker/docker-compose.prod.yml up -d
docker compose -f docker/docker-compose.prod.yml logs -f app
```

При каждом старте контейнер применяет миграции (`alembic upgrade head`, идемпотентно); ошибка миграции останавливает его с ненулевым кодом. PostgreSQL наружу не публикуется. Сессия Telethon и бэкапы лежат в томах `appdata` и `backups`. Healthcheck контейнера — `python -m app.health`: БД отвечает и планировщик пишет heartbeat.

## Бэкапы

`scripts/backup.py` делает дамп БД (`pg_dump -Fc`, нужен клиент PostgreSQL версии не ниже сервера) и копию файла сессии Telethon в `backup.dir` и удаляет бэкапы старше `backup.keep_days`. Пароль передаётся pg_dump через `PGPASSWORD`, а не аргументом. Запуск там, где БД доступна напрямую, раз в сутки через cron:

```
0 3 * * * cd /opt/news_bot && .venv/bin/python scripts/backup.py >> logs/backup.log 2>&1
```

В боевом compose БД не опубликована наружу, а в образе приложения нет pg_dump, поэтому на сервере делайте дамп через контейнер БД:

```
0 3 * * * cd /opt/news_bot && docker compose -f docker/docker-compose.prod.yml exec -T postgres sh -c 'pg_dump -Fc -U "$POSTGRES_USER" "$POSTGRES_DB"' > backups/db_$(date -u +\%Y\%m\%dT\%H\%M\%SZ).dump
```

Восстановление: `pg_restore --clean -d <база> <файл.dump>`.

## Отчёт по тестовому прогону

```bash
.venv/bin/python scripts/run_report.py --from 2026-10-10 --to 2026-10-14
```

Печатает число публикаций, медиану и p95 задержки от публикации в источнике до канала, долю отклонённых модератором, пойманные дубли по уровням, долю дублей в канале, расход DeepSeek по дням, ошибки источников и таблицу ok/fail по целям из секции `metrics`. Даты — включительно, в часовом поясе `app.timezone`.

Порог SimHash подбирается на размеченном вручную наборе (около 200 новостей, JSONL с полями `id`, `title`, `text`, `cluster`): `.venv/bin/python scripts/eval_dedup.py <файл.jsonl>`; рекомендованное значение впишите в `dedup.simhash_max_distance`.

**Почему порог не больше 3.** Похожие новости ищутся не перебором всего окна, а по индексу: 64-битный SimHash разбит на четыре части по 16 бит (`news_items.simhash_b0`…`simhash_b3`, каждая со своим индексом вместе с `created_at`). Если расстояние Хэмминга не больше 3, то различий меньше, чем частей, и хотя бы одна часть совпадает точно — по ней и находится кандидат, а точное расстояние считается уже только для кандидатов. При пороге 4 и выше дубль можно было бы пропустить, поэтому такое значение конфигурации отклоняется при запуске с объяснением.

## Частые проблемы

**FloodWait от Telegram.** Telethon просит подождать перед следующим запросом. Бот ждёт сам (`telegram.flood_wait_*`); если ожидание длиннее `flood_wait_max_s`, канал получает ошибку и опрашивается позже. Частые FloodWait — признак слишком большого числа каналов или частых перезапусков: уменьшите `catch_up_limit`.

**Сломался парсер сайта.** Сайт сменил вёрстку — `/sources` -> «проверить» показывает 0 материалов или ошибку, после `collectors.max_consecutive_errors` ошибок подряд приходит алерт «Источник не отвечает». Откройте страницу-список, подберите новые CSS-селекторы и пересоздайте источник через `/add_source` (старый удалите в `/sources`). Сайты, запрещающие обход в robots.txt, не собираются.

**Превышен бюджет DeepSeek.** При достижении `ai.daily_budget` приходит алерт, обработка моделью останавливается до следующих суток по `app.timezone`, новости ждут в статусе `normalized` и обработаются потом. Поднимите бюджет в `configs/base.yaml` (или `AI__DAILY_BUDGET`) и перезапустите приложение.

**Модель недоступна или отклоняет запросы.** Приходит алерт `ai_down`: проверьте ключ, баланс и `DEEPSEEK_BASE_URL`. Новости остаются `normalized` и обработаются после восстановления.

**Посты не выходят.** Проверьте `/status`: пауза, тихие часы (`publisher.quiet_hours`), интервал между постами, права бота в канале. Ошибка публикации приходит алертом `publish_error`.
